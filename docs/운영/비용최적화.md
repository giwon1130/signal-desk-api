# 비용 최적화 (백엔드 기준)

## 2026-10-16 운영 기준값

Railway를 읽기 전용으로 확인한 값이다. 청구 주기는 2026-09-23~10-23이며 아래는 확정 월 청구액이 아닌 10-16까지의 사용액이다.

| 항목 | 사용액 |
|---|---:|
| 전체 프로젝트 | $17.25 |
| 전체 메모리 | $17.02 (약 99%) |
| 시데 API | $6.61 (그중 메모리 $6.58) |
| 시데 Postgres | $0.62 |
| 시데 합계 | $7.23 (전체 약 42%) |

전체 청구 주기 예상 사용액은 약 $22.92였다. Pro의 월 최소 $20와 포함 사용액을 고려하면 자원 절감액과 실제 청구 절감액은 다를 수 있다. Gemini 등 외부 공급자 비용은 이 수치에 포함되지 않는다.

- API 최근 7일 메모리 시간별 관측 평균 약 0.89GB. 배포 직전 1시간 평균 938.5MB, CPU 평균 0.0016vCPU.
- 최근 6시간 HTTP 358건/5xx 0건. 요청 수는 사용자 수가 아니며 폴링도 포함한다.
- API/DB 각 1개 replica, 별도 preview 환경 없음. DB는 내부망 연결. 일반 시장 캐시 워머는 이미 기본 비활성.

## 메모리 반환

Docker 실행값은 Java 21 `-Xms128m -Xmx768m -XX:+UseG1GC`를 유지한다. 처리량 피크를 검증하지 않고 heap이나 컨테이너 상한을 급격히 낮추지 않는다.

추가값:

```text
-XX:G1PeriodicGCInterval=60000
-XX:+G1PeriodicGCInvokesConcurrent
-XX:G1PeriodicGCSystemLoadThreshold=0
-XX:MinHeapFreeRatio=10
-XX:MaxHeapFreeRatio=30
```

GC가 60초 동안 발생하지 않았을 때 G1의 동시 수집을 검토하고, 필요 없는 heap 여유분을 반환한다. 공유 호스트의 load average 때문에 이 작업이 계속 취소되지 않도록 load 임계값은 0(비활성)이다. 매분 강제 Full GC 또는 애플리케이션 `System.gc()` 호출이 아니다. RSS는 heap 외 메타데이터·스레드·네이티브 버퍼도 포함하므로 768MB 이하가 보장되는 설정은 아니다.

- [Java 21 G1의 heap 크기와 주기적 GC](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html)
- [Java 21 heap 여유 비율](https://docs.oracle.com/en/java/javase/21/docs/specs/man/java.html)

## 조회 없는 선계산 줄이기

| 설정 | 기본 | 영향 |
|---|---|---|
| `SIGNAL_DESK_MARKET_CACHE_WARM_ENABLED` | false (기존) | 일반 시장 화면의 30초 선계산 |
| `SIGNAL_DESK_SECTOR_ROTATION_WARM_ENABLED` | false | 부팅 3분 후/매일 05:30의 18개 ETF 장기 분석 선계산 |
| `SIGNAL_DESK_MOVER_REASON_WARM_ENABLED` | false | 정규장 중 15분마다 변동 종목 보도 선조회 |

선계산만 중단한다. 섹터 로테이션/종목 변동 근거 API는 실제 요청 시 계산하고 캐시한다. 최초 조회는 선계산이 있을 때보다 느릴 수 있다. 실패/빈 자료를 정상 분석처럼 캐시하지 않는 기존 동작도 유지한다. 필요하면 해당 옵션만 true로 되돌릴 수 있다.

## 캐시 보관량과 만료 정리

- 장기 Yahoo 일봉은 60개 티커 대신 **총 60,000봉**으로 보관량을 제한한다. 3년/20년 응답의 크기 차이를 반영하며, 조회/분석 기간이나 원자료를 잘라서 계산하지 않는다. 일봉 개수는 메모리 크기의 대용치이지 바이트 단위 제한은 아니다.
- 기존 시세·뉴스·거시·브리프 캐시 TTL은 유지한다.
- Caffeine의 공유 `Scheduler.systemScheduler()`로 요청이 없어도 만료 객체를 정리한다. 캐시 정리는 외부 호출이나 재계산을 발생시키지 않는다.
- [Caffeine 공식 만료/가중치 설명](https://github.com/ben-manes/caffeine/wiki/Eviction)

## 유지하는 브리프·알림

모닝 08:30, 한국 마감 15:40, 미국 마감 06:30, 흐름 리딩/뉴스 다이제스트, 관심종목/리딩 콜, 공시 수집·알림, 일별 관측 저장, 저장된 시즌 규칙 알림은 이번 변경 대상이 아니다. scheduler pool 6개·HTTP pool 12개·시장 코어 pool 8개, 거래일/시간대 가드, 중복 발송 방지와 데이터 품질 규칙도 유지한다.

서버는 상시 실행한다. Railway Serverless로 재우면 내부 스케줄이 정시에 실행되지 않을 수 있으므로 이번에는 사용하지 않는다. DB 이전이나 데이터 삭제도 필요하지 않다.

## 검증·운영 확인

1. Java 21 전체 테스트와 `bootJar`.
2. 선계산 기본 비활성/옵션 복구, 브리프·한미 관심종목/리딩 알림 dispatch, 요청 기반 섹터 계산/캐시 재사용, 60,000봉 예산을 검증.
3. 같은 Java 21/최대 heap에서 일시 할당 후 유휴 상태의 heap 반환을 비교. 합성 프로브의 결과는 운영 RSS 절감률로 표시하지 않는다.
4. 배포 후 `/health`의 `storeMode=jdbc, db=up`, 시장/브리프 조회, 재시작·OOM·스케줄 오류 및 RAM을 확인.
5. 부팅 직후의 낮은 RAM만으로 절감을 확정하지 않는다. 평일 브리프·정규장 작업을 포함한 24~48시간 평균을 기존 0.89GB와 비교한다. 월 예상액은 관측 평균으로 다시 계산한다.

문제 발생 시 해당 커밋을 revert해 다시 배포한다. heap 부족이 관측되지 않는 한 `-Xmx`를 더 줄이지 않는다. CORS는 브라우저 출처 보호이며 비브라우저 봇의 비용 방어 수단으로 간주하지 않는다. Railway의 서비스 빌드는 무료이므로 빌드 횟수를 이번 비용 원인으로 보지 않는다.
